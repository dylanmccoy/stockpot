## Problem Statement

Phase 2 shipped working authentication, but three defects and one divergence
sit underneath it. None is visible in a green test suite.

**A save can fail and still report success.** The request-scoped session commits
after the response has already been generated. When that commit fails — a
constraint violation, or write-lock contention — the framework locates the
error handler, refuses to use it because the response has started, and the
caller receives `200` with the data silently discarded. The documented promise
that conflicts surface as `409` and never as `500` is not true for anything that
fails at commit time. For a household recipe box, a write that reports success
and stores nothing is the one failure it cannot absorb.

**A forgotten password is unrecoverable.** There is no way to change a password
through the API. Registration is disabled by default, there is no email service,
and the deployment is LAN-only — so the only remedy is a `sqlite3` shell against
the database file. A household member who shares or loses a credential has no
way to rotate it, and no way to sign out a device they no longer control.

**Timestamps lose their timezone.** Every datetime column is declared
timezone-aware, but SQLite has no timezone type and returns the value naive. The
contract promises ISO 8601 with an explicit UTC offset on every response; every
read path emits an offset-less string instead. One comparison in the auth path
already carries a hand-written workaround for this, which is evidence of the
problem rather than a fix for it.

**Session lifetime configuration has no effect.** Token issuance reads the
lifetime from a module-level configuration object rather than the one the
running application was built with. Setting it per-application does nothing —
which also means the test suite cannot produce an expired token by configuring
one, and reaches into the database to rewrite the expiry column instead.

## Solution

Four changes, all inside the modules Phase 2 already owns.

**Move the transaction boundary inside the window where errors can still be
reported.** A route-class wrapper commits after the endpoint returns but before
the response is built, so a commit-time failure converts to `409` exactly like a
failure raised inside a handler. A guard test makes it impossible for a
later-phase router to be wired without it.

**Add a password-change endpoint.** Authenticated, requires the current
password, invalidates every existing session for that user, and returns a fresh
token in the same shape login returns — so the device that changed the password
stays signed in and every other device is signed out.

**Attach UTC once, in the persistence layer.** A column type re-attaches the
offset on every read, so the guarantee holds for every field on every endpoint —
including paths that bypass the ORM. The ad-hoc workaround in the auth path is
deleted. Timestamps are generated by one Python clock rather than a mix of
application and database defaults.

**Make session lifetime a real knob.** Token issuance takes configuration as an
argument, and the configuration rejects a negative lifetime outright.

## User Stories

1. As a household member, I want to change my password through the API, so that I don't need a database shell to rotate a credential.
2. As a household member, I want to prove I know my current password before changing it, so that someone with my unlocked device cannot silently take over the account.
3. As a household member, I want a distinct, clear error when my current password is wrong, so that I can tell it apart from having been logged out.
4. As a household member who suspects a credential leaked, I want every existing session invalidated when I change my password, so that the leak stops mattering immediately.
5. As a household member, I want a fresh token returned by the password change, so that I stay signed in on the device I changed it from.
6. As a household member, I want my other devices signed out after a password change, so that I re-authenticate them deliberately rather than assuming they are safe.
7. As an API client, I want the password-change response to have the same shape as the login response, so that I can reuse my existing token-handling code.
8. As a household member, I want a too-short new password rejected the same way registration rejects it, so that password rules are consistent across the API.
9. As a household member, I want a failed save reported as a failure, so that I never believe a recipe was stored when it was not.
10. As an API client, I want a conflicting write to return `409`, so that I can retry or surface a meaningful message instead of guessing.
11. As an API client, I want a write blocked by database contention to return `409` rather than a success or a `500`, so that my retry logic is straightforward.
12. As a household member, I want a partly-failed operation to leave no partial data behind, so that inventory and cook history never disagree with each other.
13. As an API client, I want every timestamp to carry an explicit UTC offset, so that I can parse it without guessing a timezone.
14. As an API client, I want a recipe's last-updated timestamp to change when I replace it, so that I can tell a stale cached copy from a fresh one.
15. As an API client, I want created and updated timestamps to be equal on a freshly created resource, so that "never edited" is detectable without a separate flag.
16. As an API client, I want timestamps to carry sub-second precision, so that two events in the same second still order deterministically.
17. As an API client, I want the timestamp guarantee to hold on every endpoint, so that I do not have to special-case particular fields.
18. As an operator, I want session lifetime to come from configuration the running application actually reads, so that setting it has an effect.
19. As an operator, I want a negative session lifetime rejected at startup, so that I find the mistake immediately rather than through unexplained authentication failures.
20. As an operator, I want a zero-day session lifetime to remain legal, so that I can deliberately configure instantly-expiring tokens.
21. As an operator, I want the registration bootstrap procedure to be the documented path, so that I can stand up a fresh deployment without guessing.
22. As a developer, I want timezone attachment handled in one place, so that a new datetime column cannot reintroduce offset-less output.
23. As a developer, I want the additive inventory write to use the same clock as the ORM, so that a row's timestamp does not depend on which code path touched it.
24. As a developer, I want the ad-hoc timezone workaround in the auth path deleted, so that there is one mechanism rather than two.
25. As a developer, I want token issuance to be a function of its arguments, so that it is testable without global state.
26. As a developer, I want to test token expiry by configuring the application, so that the test does not reach into the database and rewrite rows.
27. As a developer, I want the transaction boundary to live in one place, so that a route author cannot forget it.
28. As a developer, I want a test that fails when a new router is wired without the transaction boundary, so that later phases cannot silently reintroduce the silent-data-loss bug.
29. As a developer, I want routes that touch no database to require no special handling, so that adding a health-style endpoint stays trivial.
30. As a developer, I want the flush operation to mean only "give me a generated identifier", so that I am not relying on it as an error-handling mechanism.
31. As a developer, I want a test that exercises a failure at commit time specifically, so that the existing error-handler tests are not the only evidence.
32. As a reviewer, I want this work to arrive as one reviewable diff against a green baseline, so that the non-author review gate is satisfiable.
33. As a future maintainer, I want the reasons for these changes recorded alongside the changes, so that I do not undo them as unnecessary complexity.

## Implementation Decisions

### Transaction ownership

- **A route class owns the commit.** A subclass of the framework's route type
  wraps the endpoint: it runs the endpoint, then commits, then returns the
  response. Because the wrapper executes inside the exception-handling window
  and before the response is sent, a commit-time error reaches the registered
  handlers and converts to `409` like any in-handler failure. **Verified by
  prototype** during the design session — the trimmed shape that encodes the
  decision:

  ```python
  class TransactionRoute(APIRoute):
      def get_route_handler(self):
          original = super().get_route_handler()
          async def custom(request: Request) -> Response:
              response = await original(request)   # endpoint ran and serialized
              db = getattr(request.state, "db", None)
              if db is not None:
                  db.commit()
              return response
          return custom
  ```

  Response serialization completes before the commit, so no ORM attribute is
  accessed post-commit and expiry-on-commit needs no configuration change.

- **The route class lives in the database module,** beside the session
  dependency. It cannot live in the application-assembly module: routers must
  reference it when they construct their router object, and routers cannot
  import the assembly module without a cycle.

- **The session dependency stops committing.** It keeps rollback-on-exception
  and close, and additionally stashes the session on the request state. The
  route class reads it from there and no-ops when absent, so a route with no
  database dependency needs no special casing.

- **Every router passes the route class at construction.** The route class is a
  property of the router a route is declared on, and router inclusion cannot
  apply it retroactively. This is a wiring obligation, enforced by a test rather
  than by convention — see Testing Decisions.

- **Unchanged behavior:** a route raising a not-found error still rolls back, so
  the authenticated last-used bump is still lost on an error response. This
  matches today.

- **The flush operation reverts to one job:** call it when a generated
  identifier is needed. It is no longer load-bearing for error handling.

### Password change

- **A new authenticated endpoint on the auth router**, taking the current and
  new passwords.
- **Check order:** body validation failure → `422`; current password incorrect →
  `403` with a distinct message. The caller's token is valid and the *action* is
  refused, so `401` would wrongly instruct the client to re-authenticate.
- **The new password uses the same length rule registration uses.**
- **On success:** replace the stored hash, delete **every** session row for that
  user including the caller's, issue a fresh token, and return the same response
  model login returns, with `200`.
- Deleting all sessions unconditionally — rather than excepting the caller's —
  keeps revocation a single unconditional operation with no special case, and a
  full-window reset is the intent behind changing a password.

### Datetimes

- **A custom column type re-attaches UTC on read**, applied to every datetime
  column across every model. This is the only mechanism that holds for read
  paths that bypass the ORM.
- **The hand-written naive-datetime normalization in the auth expiry comparison
  is deleted.** The column type makes it redundant.
- **All timestamps are generated Python-side**: creation defaults and
  update-triggered bumps both call the application's UTC clock. The database's
  own current-timestamp function is not used — it produces a naive,
  second-precision value that would defeat the column type and lose ordering
  precision.
- **The additive inventory write binds an explicit timestamp parameter.** It is
  an upsert statement, so it bypasses ORM update-triggered defaults by
  construction.
- **Documentation change:** the data-model section currently describes these as
  database-side defaults. That wording is corrected to Python-side as part of
  the spec-edit PR.

### Configuration and token issuance

- **Token issuance takes the settings object as an argument.** Both call sites
  are on the auth router, which already receives settings by injection. This
  removes the last module-global configuration read from a request path.
- **Session lifetime is constrained to zero or greater.** Zero is meaningful and
  deliberately allowed: it is the clean way to produce an instantly-expired
  token for testing. Negative is pure misconfiguration and is rejected when
  settings are constructed.
- **The two remaining import-time module globals are left alone** — they are the
  documented server entrypoint, and the engine is lazy, so the import-time
  construction opens no connection.

### Documentation contract changes (spec-edit PR, prerequisite)

The transaction-ownership paragraph is rewritten to name the route class as
owner, state that the session dependency keeps rollback and close, narrow the
flush rule, and state explicitly that a commit-time conflict or write-lock now
converts to `409`. The auth section gains the password-change endpoint, the
infrastructure sections gain the column type and route class, the token-issuance
signature is updated, and the acceptance matrix gains the rows named below.

## Testing Decisions

**What makes a good test here.** Assert observable behavior through the widest
seam that can see it: response status, response body, and what a subsequent
request observes. Do not assert that a particular function was called, that a
column has a particular default, or that a class has a particular base. Three of
these changes are invisible from the outside by nature — configuration
validation, route wiring, and commit-time failure — and those are called out
below with the narrower seam each requires and the prior art it follows.

**Primary seam — real HTTP over the factory-built application.** The existing
anonymous and authenticated client fixtures build the app through the production
factory over an in-memory engine carrying the production connection listeners,
with no dependency overrides. Everything that can be tested here, is:

- Every response datetime ends with an explicit UTC offset — assert across a
  representative endpoint per model rather than one field.
- Replacing a recipe advances its updated timestamp; a freshly created resource
  has equal created and updated timestamps.
- Password change: wrong current password → `403`; short new password → `422`;
  success → `200` with a token that works, the old token rejected, and a second
  device's token rejected.
- Token expiry: build the application with a zero-day session lifetime and
  assert a freshly issued token is refused. **This replaces the existing test's
  direct database manipulation of the expiry column — delete that reach-around.**

**Commit-time failure — a throwaway route on a locally built application.**
Prior art already exists in the suite: the exception-handler tests construct a
local application instance and attach a test-only route that raises. Follow that
pattern with a route that leaves the session in a state that fails at commit,
and assert `409` with the conflict body. Today's tests raise from inside the
route body, which is the path where handlers already worked — this is the half
that was never covered.

**Configuration validation — direct construction.** Constructing settings with a
negative session lifetime raises a validation error; zero is accepted. Prior art:
the engine-listener tests assert against a constructed object rather than
through HTTP.

**Route wiring — introspection of the built application.** Iterate the built
application's routes and assert that every API route depending on a database
session uses the transaction route class. This is the only mechanism that fails
when a later phase adds a router and forgets the wiring; a behavioral test would
pass, because the bug is silent by definition.

**Modules under test:** the auth router, the persistence layer's session and
route-class behavior, the models' timestamp behavior, and the settings object.

**Suite-wide expectation:** the full backend suite is green at the end, not only
the new tests.

**Evidence behind the commit-time defect.** A dependency raising after yield,
with a handler registered for that exception type, returns `200` with the
response body of a successful call under the real server configuration; with
server exceptions raised, the framework reports that it caught a handled
exception but the response had already started. Both were reproduced during the
design session, as was the route-class fix returning `409`.
